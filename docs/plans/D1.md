# D1 plan — integrate/waves.py: conflict graph → waves

## 1. Goal
Pure, offline function that turns a set of `Plan`s into ordered `Wave`s such that no two issues in a wave
touch the same file (or the same verified function) and no wave carries more than one migration. Plus a
plain-text renderer the CLI can print. No sandbox, no LLM, no new schema fields.

## 2. Files and signatures
`warden/integrate/waves.py` (fill the stub; keep module docstring). Public surface:

- `MIGRATION_MARKERS: tuple[str, ...] = ("alembic/versions/", "migrations/")`
- `is_migration(path: str) -> bool` — true iff any marker is a substring of the normalised path
  (`path.replace("\\", "/")`, leading `./` stripped, `::selector` removed). Conservative on purpose:
  `db/migrations/README.md` counts; a false positive only costs parallelism.
- `plan_is_migration(plan: Plan) -> bool` — any entry of `files_to_touch` is a migration.
- `conflicts(a: Plan, b: Plan, functions: Mapping[str, set[str]] | None = None) -> bool`
- `plan_waves(plans: Sequence[Plan], *, functions: Mapping[str, set[str]] | None = None,
  max_wave_size: int = 4) -> list[Wave]`
- `render_waves(waves: Sequence[Wave]) -> str`

Default `max_wave_size=4` mirrors `WARDEN_MAX_FORKS` but is a plain arg: waves.py must not import
config (keeps it pure/offline; the CLI passes `settings.max_forks` later).

### Conflict definition (decided)
An entry in `files_to_touch` is either a bare path `p` or a selector `p::name` (pytest-style; the Planner
prompt may emit these later — today it emits bare paths, which is the safe default).
Two plans conflict iff they share a normalised path `p` **unless all** of: (1) `functions` is given and
`p in functions`; (2) both plans list `p` only via `::name` selectors (no bare `p` on either side);
(3) every selector name on both sides is in `functions[p]`; (4) the two selector sets are disjoint.
Why this shape: file-level is what git actually conflicts on, the `Plan` schema has no per-issue function
field (so file→functions cannot be attributed to an issue any other way without a forbidden schema change),
and validating selectors against the box's `grep -n "def "` output means a hallucinated function name
degrades to the conservative file-level rule instead of silently allowing a merge conflict. With
`functions=None` the whole refinement is inert — zero risk to today's callers.

### Wave assignment (deterministic greedy first-fit)
1. Validate: `max_wave_size >= 1` else `ValueError`; duplicate `issue` numbers → `ValueError`.
2. Sort plans by `issue` ascending (input order is irrelevant to output).
3. For each plan in that order, put it in the **lowest-numbered** existing wave where: no member conflicts
   with it; `len(issues) < max_wave_size`; and, if the plan is a migration, the wave has no migration yet.
   Otherwise open a new wave. (Pure function; no heuristics on `landing_order`, `risk_class`, size.)
4. Waves numbered from 1; `issues` ascending by construction; `integration_image_uuid=None`, `merged=[]`.
Empty input → `[]`. Non-optimal colouring is acceptable and stated; determinism and readability win.

### `render_waves`
Fixed-width table, no colour/ANSI (colour is cli's job), trailing newline, empty input → `"no waves\n"`:
```
Wave  Issues                  Image     Merged
1     #101 #102 #104 #106     —         —
2     #103 #105               ab12cd34  #103
```
Image column shows the first 8 chars of `integration_image_uuid` or `—`; Merged shows `#n` list or `—`.

## 3. Tests — `tests/test_waves.py` (new)
Helper `mk(issue, *files, risk=("none",))` builds a `Plan` with dummy summary/tests/citations.

Six-issue Fabric-style fixture (`FIX6`):
| issue | files_to_touch |
| 101 | backend/app/services/invoices.py, backend/tests/test_invoices.py |
| 102 | backend/app/api/vouchers.py, backend/tests/test_vouchers.py |
| 103 | backend/app/services/invoices.py, backend/app/services/tax.py |
| 104 | backend/alembic/versions/0042_voucher_idx.py, backend/app/models/voucher.py |
| 105 | backend/alembic/versions/0043_invoice_status.py, backend/app/models/invoice.py |
| 106 | backend/app/api/payments.py |
Hand result (max 4): 101→w1; 102→w1; 103 conflicts 101 (invoices.py)→w2; 104 migration, w1 has none→w1;
105 migration, w1 already has 104→w2 (no conflict with 103)→w2; 106→w1. **Expected: [[101,102,104,106],
[103,105]]**. With `max_wave_size=3`: **[[101,102,104],[103,105,106]]**.

1. `test_six_issue_fixture_matches_hand_plan` — `[w.issues for w in plan_waves(FIX6)] == [[101,102,104,106],[103,105]]`.
2. `test_fixture_with_max_wave_size_three` — `== [[101,102,104],[103,105,106]]`.
3. `test_empty_input_returns_no_waves` — `plan_waves([]) == []`.
4. `test_all_conflicting_gives_one_issue_per_wave` — 3 plans all touching `a.py` → `[[1],[2],[3]]`.
5. `test_two_migrations_forced_into_two_waves` — 2 disjoint plans, one `alembic/versions/x.py`, one
   `db/migrations/0001.sql` → two waves; `is_migration` true for both, false for `app/migrate_helper.py`.
6. `test_determinism_ignores_input_order` — `plan_waves(reversed(FIX6)) == plan_waves(FIX6)`; running twice equal.
7. `test_max_wave_size_respected` — 5 independent plans, `max_wave_size=2` → sizes `[2,2,1]`; every wave
   `len <= max`; `max_wave_size=0` raises `ValueError`.
8. `test_duplicate_issue_raises` — two plans with issue 7 → `ValueError`.
9. `test_wave_defaults` — numbers `1..n` contiguous, `integration_image_uuid is None`, `merged == []`.
10. `test_selectors_disjoint_verified_do_not_conflict` — `a.py::foo` vs `a.py::bar`,
    `functions={"a.py": {"foo","bar"}}` → one wave.
11. `test_selectors_fall_back_to_file_level` — same plans with `functions=None` → two waves; with
    `functions={"a.py": {"foo"}}` (bar unverified) → two waves; bare `a.py` vs `a.py::foo` → two waves.
12. `test_selector_path_normalisation` — `./a.py::foo` and `a.py` conflict; migration detected through selector.
13. `test_render_waves_table` — output contains header `Wave`, `#101 #102 #104 #106` on the line starting
    `1`, `—` for missing image; wave with uuid `"ab12cd34-…"` and `merged=[103]` shows `ab12cd34` and `#103`;
    `render_waves([]) == "no waves\n"`; ends with newline; no ANSI escapes.

## 5. Risks / open questions (orchestrator rules)
- `Wave` has no `is_migration`/`files` field, so `render_waves` cannot mark the migration issue; if wanted,
  either add `Wave.migration: int | None` (schema change — forbidden here) or pass `plans` to the renderer later.
- `render_waves` is not wired into `warden` (cli.py forbidden). Follow-up: print it in `run --dry-run`.
- Cross-issue dependencies ("fix B needs A merged") are not expressible in `Plan`; waves ignore them.
  `landing_order` is per-issue file order and is intentionally unused.
- `risk_class == "schema"` without a migration path is *not* treated as a migration; path rule only, per brief.
- `::selector` convention is new; the Planner prompt (Phase B files) does not emit it yet — the refinement is
  dormant until then. If the orchestrator prefers no dormant code, drop tests 10–12 and rule (file-only).
- Greedy first-fit is not an optimal colouring; acceptable for ≤ ~10 issues per campaign (E2).
